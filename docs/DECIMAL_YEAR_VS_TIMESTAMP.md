# decimal-year 空间 vs 时间戳空间 —— IGRF 时间插值约定笔记

> 本文记录 libigrf 开发中关于时间插值约定的一次讨论结论。
> 英文摘要见 `IMPLEMENTATION_NOTES.md` §1；本文是完整的中文版。

## 一句话结论

**libigrf（按规范）在 decimal-year 数字空间对 Gauss 系数做线性插值；ppigrf 在真实流逝时间（时间戳）空间插值。两条"均匀轴"只在 epoch 端点重合，中间因闰年而岔开——同一物理时刻，两种约定取出略不同的系数集。这是纯粹的约定差异，不是误差，场级量级 ~0.1–0.2 nT。**

## 1. 两种约定

| | 插值空间 | 插值参数 |
|---|---|---|
| libigrf（规范 §6.3） | decimal-year 数字 | `f = (Y − E1)/(E2 − E1)`，纯算术，不经日历 |
| ppigrf（pandas `interpolate(method='time')`） | 真实流逝时间（int64 纳秒） | `f = elapsed(t − t₁)/elapsed(t₂ − t₁)` |

## 2. 根源：decimal year 不是均匀的时间刻度

平年 365 天、闰年 366 天，所以"日历日期 → decimal year"的映射是**分段线性**的，每个年份边界一个拐点（斜率 1/365 vs 1/366）。时间戳轴则严格均匀（1 天永远是 1 天）。两条轴在 epoch 端点精确一致（f=0 与 f=1），中间必然分岔。

## 3. 实例：2025–2030 区间的"中点"

该区间含 1 个闰年（2028），共 **1826 天**。decimal year 2027.5（2027 为平年）= 日历时刻 2027-07-02 12:00：

| | decimal-year 空间（规范） | 时间戳空间（pandas） |
|---|---|---|
| 插值参数 f | (2027.5 − 2025)/5 = **0.5**（精确） | 912.5/1826 ≈ **0.499726** |

Δf ≈ 2.7×10⁻⁴ × 5 年 ≈ **12 小时的等效时间偏移**。规范约定下 f = 0.5 的中点实际落在 **2027-07-03 00:00**，比日历中点晚半天。

## 4. 实测量级

在同一时刻（2027-07-02 12:00）分别按两种 f 取系数求场，5 个全球测点上的最大分量差为 **0.1845 nT**（当前世代 2025–2030 的 SV 是 IGRF 历史上最强的）；同样的 12 小时对比在 1950–1955 区间只有 ~0.07 nT——量级随时代 SV 强度缩放。早期开发记录里写的 "~0.05 nT" 估计偏低，以本文实测为准。

顺带修正一个曾用错的演示例子：**2020–2025 区间的 2022.5 恰好精确等于 f = 0.5**（闰年 2020 与 2024 关于中点对称），不能用来演示差异。好例子是 2027.5（上表）、2021.0（f_ts = 0.200328 ≠ 0.2），以及一切闰年的 X.5——闰年的日历中点是 7 月 3 日 00:00，不是 7 月 2 日 12:00。

## 5. "每天增量"的视角

| | 均匀的轴 | 一天的系数增量 |
|---|---|---|
| libigrf / 规范 | decimal-year 数字 | 平年 SV/365，闰年 SV/366；比值精确 = 366/365 ≈ 1.00274（实测 1.002740 吻合） |
| ppigrf | 真实流逝时间 | **恒定**（实测 2027 平年与 2028 闰年每天变化完全相同），且连续到纳秒（每秒增量 = 每天/86400 精确成立） |

ppigrf 的完整流水线：SHC 文件里的 epoch（decimal year）→ 时间戳，只在**读文件时**换算一次（`yearfrac_to_datetime`，365/366 day-count）；用户输入本来就是 datetime；插值完全在流逝时间上进行。注意 `method='time'` 对它是实质性的——相邻 epoch 间隔的真实天数并不均匀（1826 与 1827 天交替），若用按位置等分的 `linear` 插值就会算错。

## 6. 与 IGRF 官方定义的关系

- 官方（IGRF-14 论文，Beggan et al.）：SV 系数单位 **nT/year**，定义为未来 5 年窗口内 Gauss 系数变化的**线性近似**；求值约定 = 1900–2025 分段线性插值 + 2025–2030 用 SV 外推 `g(t) = g(2025.0) + (t − 2025.0)·SV`。外推是**连续线性斜坡**（2027.4 用 2.4×SV），不逐年跳变，"天"不进入 SV 的算术。
- SHC 文件的 2030 列 = 2025 列 + 5.0×SV，由 IGRF-14 工作组预制。验证：全部 195 个隐含 SV = (C₂₀₃₀ − C₂₀₂₅)/5 精确落在 0.1 nT/yr 网格上（最大残差 5.7×10⁻¹⁴，纯浮点噪声）——SV 官方发布精度即 0.1 nT/yr。
- **代数恒等**：在 [2025, 2030] 内，对预制好的 2030 端点做线性插值 ≡ 官方 SV 外推（两者都是 `g(2025) + (t−2025)·SV`）。这就是规范要求 libigrf 不单独实现 SV 逻辑的原因——SHC 已把 SV 编码进端点，一套"epoch 系数 + 统一线性插值"覆盖全程 1900–2030。
- 官方论文只说时间"以年为单位"，**没有钉死 day-count**。365/366 是 SHC/ppigrf/本项目规范采用的具体约定；若某实现用 365.25 的儒略年约定，其"每天增量"就会完全均匀。闰年不均匀性属于约定家族，不属于 IGRF 数学定义本身。

## 7. 工程处理（本项目的做法及理由）

- libigrf 遵循规范：decimal-year 空间插值。KISS，库里没有任何日历运算。
- `tools/generate_reference.py` 生成 ppigrf 回归数据时，把求值时间戳对齐到 `t = T1 + f·(T2 − T1)`，使 pandas 的插值参数恰好等于规范要求的 f——两边使用同一组系数，比较的才是场计算本身（实测一致性 ~5×10⁻⁸ nT）。
- 反过来，直接拿两个实现按"同一日历日期"对比，会看到 ~0.1–0.2 nT 的差异：**那是约定差异，不是 bug**，排查时不要把它当成实现错误去"修"。
